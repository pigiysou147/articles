# 高并发实战：分布式锁与幂等性设计

## 背景
在电商大促场景下，库存扣减、优惠券领取等接口面临巨大的并发压力。如果处理不当，很容易出现**超卖**（库存变成负数）或者**重复领取**的问题。本文总结了我在项目中处理这两个核心问题的方案。

## 1. 为什么需要分布式锁？
在单机环境下，`synchronized` 或 `ReentrantLock` 可以解决线程安全问题。但在微服务多实例部署的场景下，本地锁失效，必须使用分布式锁。

## 2. 基于 Redis 的分布式锁实现
虽然 Zookeeper 也能做，但 Redis 性能更好，且我们在项目中本身就重度依赖 Redis。

### 2.1 基础实现 (SetNX)
```java
// 伪代码
String result = jedis.set(lockKey, requestId, "NX", "PX", expireTime);
if ("OK".equals(result)) {
    try {
        // 执行业务逻辑
    } finally {
        // 释放锁：注意要判断是否是自己的锁，防止误删
        if (requestId.equals(jedis.get(lockKey))) {
            jedis.del(lockKey);
        }
    }
}
```
**坑点**：释放锁的操作不是原子的。如果 `get` 之后判断成功，但在 `del` 之前锁过期了且被别的线程抢占，就会误删别人的锁。
**解法**：使用 Lua 脚本保证原子性。

### 2.2 生产级方案：Redisson
手写 Redis 锁容易踩坑（比如锁续期问题），推荐使用 Redisson。

```java
RLock lock = redissonClient.getLock("stock_lock_" + skuId);
try {
    // 尝试加锁，等待10秒，锁自动过期时间30秒
    // Redisson 内部有 Watch Dog 机制，会自动给锁续期
    boolean isLocked = lock.tryLock(10, 30, TimeUnit.SECONDS);
    if (isLocked) {
        // 扣减库存
    }
} catch (InterruptedException e) {
    // 处理异常
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

## 3. 接口幂等性设计
解决了并发问题，还得解决**重复请求**问题（网络超时重试、用户狂点按钮）。

### 3.1 什么是幂等性？
对于同一个操作，无论请求多少次，结果都是一致的，不会产生副作用。

### 3.2 常见方案
1.  **数据库唯一索引**：最强兜底。比如流水表建立 `order_id` 的唯一索引，重复插入直接报错。
2.  **Token 机制**：
    *   进入页面前先请求后端获取一个 Token，存入 Redis。
    *   提交表单时带上 Token。
    *   后端验证 Token 是否存在，存在则删除并执行业务；不存在说明是重复提交。
    *   *注意*：验证和删除必须是原子操作（Lua脚本）。

### 3.3 状态机幂等
对于订单状态流转，使用状态机控制。
```sql
UPDATE order SET status = 'PAID' WHERE id = 123 AND status = 'CREATED';
```
利用 `WHERE` 条件检查前置状态，如果状态已经被修改，则更新行数为 0，视为幂等成功。

## 总结
- **高并发写**：Redis 分布式锁（推荐 Redisson）。
- **防重复提交**：Token 机制 + 数据库唯一索引兜底。
- **核心原则**：永远不要信任前端的防抖，后端必须有自己的防线。
