# 高并发实战：分布式锁的 CP 模型与 Redisson 源码剖析

## 背景
在电商大促场景下，库存扣减、优惠券领取等接口面临巨大的并发压力。常见的“超卖”问题，本质上是分布式系统下的**数据一致性**问题。
本文不谈基础用法，我们将深入 Redis 分布式锁的底层实现，探讨 Lua 脚本原子性、WatchDog 机制以及 CAP 定理下的取舍。

## 1. 为什么 `setnx` 还是不够好？
早期的 Redis 锁实现往往是 `setnx` + `expire`。但这两个指令是非原子的。如果在 `setnx` 成功后、`expire` 执行前机器宕机，就会造成**死锁**。
虽然 Redis 2.6.12 引入了 `SET key value [EX seconds] [PX milliseconds] [NX|XX]` 复合指令解决了原子性问题，但依然无法解决**锁误删**和**锁续期**的问题。

## 2. Redisson 核心机制剖析

### 2.1 锁的底层结构：Hash 而非 String
很多人认为分布式锁就是一个 Key-Value String。但在 Redisson 中，锁的类型是 **Hash**。
Key: `lock_key`
Field: `UUID + ThreadID`
Value: `重入次数 (counter)`

**技术细节**：为什么用 Hash？为了实现**可重入锁 (ReentrantLock)**。
当同一个线程再次请求锁时，Redisson 只会通过 Lua 脚本将 Value + 1，而不是阻塞。这与 JDK `ReentrantLock` 的 `state` 设计异曲同工。

### 2.2 核心 Lua 脚本解读
让我们看看 `tryLockInnerAsync` 的源码（简化版）：

```lua
-- 1. 如果锁不存在
if (redis.call('exists', KEYS[1]) == 0) then
    redis.call('hset', KEYS[1], ARGV[2], 1); -- 创建 Hash，计数为 1
    redis.call('pexpire', KEYS[1], ARGV[1]); -- 设置过期时间
    return nil;
end;
-- 2. 如果锁存在，且是当前线程持有的（重入）
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    redis.call('hincrby', KEYS[1], ARGV[2], 1); -- 计数 + 1
    redis.call('pexpire', KEYS[1], ARGV[1]); -- 刷新过期时间
    return nil;
end;
-- 3. 锁被别人持有，返回剩余存活时间
return redis.call('pttl', KEYS[1]);
```
**思考**：为什么必须用 Lua？
因为 Redis 的事务（MULTI/EXEC）是弱事务（不支持回滚，仅保证执行顺序），且无法在中间根据查询结果做逻辑判断（如 `if exists`）。Lua 脚本在 Redis 中是**原子执行**的（Redis 单线程模型保证了脚本执行期间不会插入其他命令），完美解决了 check-and-set 的竞态条件。

### 2.3 WatchDog 看门狗机制
如果业务执行时间超过了锁的过期时间（默认为 30s），锁过期释放，其他线程进来，就会导致并发事故。
Redisson 的解决方案是 **TimeWheel (时间轮)** + **Netty Timer**。
当锁成功获取后，会启动一个后台任务（WatchDog），每隔 `lockWatchdogTimeout / 3` (默认 10s) 检查一次。如果当前线程还持有锁，就通过 Lua 脚本重置过期时间为 30s。
**源码细节**：WatchDog 维护在一个静态的 `ConcurrentMap` 中，基于 Netty 的 `HashedWheelTimer` 实现高效的定时任务调度，避免了创建大量线程。

## 3. Redlock 与 CAP 的权衡
在单机 Redis 下，如果主节点挂了，锁还没同步到从节点，主从切换后锁就丢失了。这是 AP 模型（高可用，但牺牲强一致性）。
Redlock 算法试图通过“在 N 个节点上分别加锁”来从概率上解决这个问题。

**但 Martin Kleppmann (DDIA 作者) 曾发文质疑 Redlock**：
他指出在分布式系统中，**NPC 问题** (Network Delay, Process Pause, Clock Drift) 是无法避免的。
*   如果 Process Pause（如 JVM STW GC） 发生在获取锁之后、操作资源之前，且 GC 时间超过了锁的 TTL，Redlock 依然会失效。
*   依赖系统时钟（Clock Drift）本身就是不安全的。

**我的观点**：
在绝大多数业务场景（如库存扣减），Redis Cluster 的最终一致性（AP）是可以接受的。如果真的涉及资金流转等强一致性场景，**不要用 Redis 锁**，请直接使用数据库的行锁（Pessimistic Locking）或者 ZooKeeper（CP 模型，利用 ZAB 协议保证强一致性）。

## 总结
分布式锁看似简单，实则暗藏玄机。从 Hash 结构的设计到 Lua 脚本的原子性，再到 WatchDog 的时间轮算法，每一个细节都是对性能与一致性的极致追求。
作为工程师，我们不应止步于 `lock()` 和 `unlock()`，而应深入理解其背后的**分布式系统理论**。
