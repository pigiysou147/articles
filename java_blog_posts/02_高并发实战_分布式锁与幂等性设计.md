# 高并发实战：分布式锁的 CP 模型与 Redisson 源码剖析

## 背景
在电商大促场景下，库存扣减、优惠券领取等接口面临巨大的并发压力。常见的“超卖”问题，本质上是分布式系统下的**数据一致性**问题。
本文不谈基础用法，我们将深入 Redis 分布式锁的底层实现，探讨 **Lua 脚本原子性**、**Netty 时间轮** 以及 **CAP 定理** 下的取舍。

## 1. 为什么 `setnx` 还是不够好？
早期的 Redis 锁实现往往是 `setnx` + `expire`。但这两个指令是非原子的。如果在 `setnx` 成功后、`expire` 执行前机器宕机，就会造成**死锁**（Key 永不过期）。
虽然 Redis 2.6.12 引入了 `SET key value [EX seconds] [PX milliseconds] [NX|XX]` 复合指令解决了原子性问题，但依然存在核心缺陷：
1.  **不可重入**：同一个线程无法再次获取自己持有的锁。
2.  **锁误删**：A 线程卡顿，锁过期释放；B 线程获取锁；A 醒来执行 `del`，把 B 的锁删了。
3.  **业务超时**：业务执行时间超过了 TTL，导致并发事故。

## 2. Redisson 核心机制源码剖析

### 2.1 锁的底层结构：Hash 而非 String
很多人认为分布式锁就是一个 Key-Value String。但在 Redisson 中，锁的类型是 **Hash**。
*   **Key**: `lock_key`
*   **Field**: `UUID:ThreadID` (客户端唯一标识 + 线程ID)
*   **Value**: `atomic_int` (重入次数 counter)

**技术细节**：为什么用 Hash？为了实现**可重入锁 (ReentrantLock)**。
当同一个线程再次请求锁时，Redisson 只会通过 Lua 脚本将 Value + 1，而不是阻塞。这与 JDK `ReentrantLock` 的 `state` 设计异曲同工。

### 2.2 核心 Lua 脚本逐行解读
Redis 的事务（MULTI/EXEC）是弱事务。为了保证 check-and-set 的原子性，Redisson 必须使用 Lua 脚本。
让我们剖析 `tryLockInnerAsync` 的源码：

```lua
-- KEYS[1]: 锁的名称
-- ARGV[1]: 锁的过期时间 (leaseTime)
-- ARGV[2]: 客户端唯一ID (UUID:ThreadID)

-- 1. 场景一：锁完全不存在
if (redis.call('exists', KEYS[1]) == 0) then
    -- 创建 Hash: hset lock_key UUID:ThreadID 1
    redis.call('hset', KEYS[1], ARGV[2], 1); 
    -- 设置过期: pexpire lock_key 30000
    redis.call('pexpire', KEYS[1], ARGV[1]); 
    return nil; -- 返回 nil 表示加锁成功
end;

-- 2. 场景二：锁存在，且是当前线程持有的（重入）
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    -- 计数器 +1: hincrby lock_key UUID:ThreadID 1
    redis.call('hincrby', KEYS[1], ARGV[2], 1); 
    -- 刷新过期时间（重置租约）
    redis.call('pexpire', KEYS[1], ARGV[1]); 
    return nil;
end;

-- 3. 场景三：锁被别人持有
-- 返回锁的剩余生存时间，供客户端等待
return redis.call('pttl', KEYS[1]);
```

**为什么 Lua 能保证原子性？**
Redis 是**单线程模型**（在处理命令时）。Lua 脚本在执行期间，Redis 不会插入其他客户端的命令。这相当于给整个脚本加了一把“大锁”，避免了竞态条件。

### 2.3 WatchDog 看门狗机制：Netty 时间轮的应用
如果业务执行时间超过了锁的过期时间（默认为 30s），锁过期释放，其他线程进来，就会导致并发事故。
Redisson 的解决方案是 **TimeWheel (时间轮)** + **Netty Timer**。

**工作流程**：
1.  加锁成功后，如果未指定 `leaseTime`，Redisson 会启动一个 `TimerTask`。
2.  该任务每隔 `lockWatchdogTimeout / 3` (默认 10s) 执行一次。
3.  任务逻辑：执行 Lua 脚本，判断锁是否还在当前线程手里。如果是，则将 TTL 重置为 30s。
4.  当业务显式调用 `unlock()` 时，会取消该任务。

**源码细节**：
Redisson 并没有为每个锁创建一个线程（那样太重了）。它复用了 Netty 的 `HashedWheelTimer`。
这是一个经典的**时间轮算法**：将时间切分为一个个 Slot（比如 100ms 一个格子），指针每滴答一次走一格。任务被挂在对应的 Slot 链表上。这使得 Redisson 能够在一个线程内高效管理成千上万个锁的续期任务。

## 3. Redlock 与 CAP 的权衡：Martin Kleppmann 的质疑

### 3.1 故障转移的困境 (Failover)
在 Redis Sentinel 或 Cluster 架构中，主从复制是**异步**的。
1.  Client A 在 Master 获取锁。
2.  Master 宕机，锁还没同步到 Slave。
3.  Slave 晋升为 New Master。
4.  Client B 在 New Master 获取同样的锁。
**结论**：Redis Cluster 是 **AP 系统**（保证可用性），无法保证强一致性（CP）。

### 3.2 Redlock 算法
为了解决这个问题，Redisson 实现了 Redlock 算法：同时向 N 个独立的 Redis 实例加锁。只要过半节点（N/2 + 1）加锁成功，就认为获取成功。

### 3.3 NPC 问题
分布式系统大神 **Martin Kleppmann** (DDIA 作者) 曾发文质疑 Redlock。他指出 **NPC 问题** 是无法避免的：
*   **N (Network Delay)**: 网络延迟。
*   **P (Process Pause)**: 进程暂停（如 JVM Full GC）。
*   **C (Clock Drift)**: 时钟漂移。

**GC 导致的致命场景**：
1.  Client A 获取了 Redlock。
2.  Client A 发生 Full GC，STW (Stop-The-World) 停顿了 40s。
3.  Redis 端的锁因为 TTL (30s) 过期而释放。
4.  Client B 获取了锁。
5.  Client A GC 结束，继续执行代码，写入数据。 -> **数据冲突！**

### 3.4 我们的选择
在绝大多数互联网业务（如库存扣减、防重提交）中，**Redis 的最终一致性是可以接受的**。极小概率的超卖可以通过后续的对账补偿解决。
但如果涉及**金融核心转账**等强一致性场景：
**不要用 Redis 锁！不要用 Redis 锁！**
请直接使用：
1.  **数据库行锁** (`SELECT ... FOR UPDATE`)。
2.  **ZooKeeper 分布式锁**：ZK 基于 **ZAB 协议**，保证强一致性。虽然性能比 Redis 差一个数量级，但它绝对可靠。

## 总结
分布式锁看似简单，实则暗藏玄机。
*   从 **Hash 结构** 的设计到 **Lua 脚本** 的原子性。
*   从 **Netty 时间轮** 的资源优化到 **CAP 理论** 的架构权衡。
每一个细节都是对系统稳定性与性能的极致追求。作为工程师，我们不应止步于 `lock()` 和 `unlock()`，而应洞察其背后的分布式原理。
