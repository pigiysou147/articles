# 重构之路：如何优雅地拯救“遗留代码”

## 背景
最近接手了一个有5年历史的老项目，代码里充斥着大量的 `if-else` 嵌套、千行类（God Class）以及不明所以的魔术数字。业务方催着加新功能，但每次修改都心惊胆战，生怕改了一个 bug 引入三个新 bug。

作为一个中级 Java 程序员，面对这种“屎山”代码，我们不能一味抱怨，而应该将其视为提升代码能力的演练场。本文将分享我在重构这个模块时的一些实战经验。

## 1. 保护现场：单元测试先行
在动任何代码之前，第一件事绝对不是改代码，而是**写测试**。
对于遗留系统，通常缺乏测试。我们可以使用 `JUnit 5` + `Mockito` 来补充核心路径的测试。

```java
// 这是一个遗留的计算逻辑，非常复杂
public class OrderCalculator {
    public BigDecimal calculate(Order order) {
        // ... 500行逻辑 ...
    }
}

// 补充测试
@Test
void should_calculate_total_price_correctly() {
    Order order = new Order(Item.of("Apple", 10.0), 2);
    BigDecimal result = new OrderCalculator().calculate(order);
    assertEquals(new BigDecimal("20.0"), result);
}
```
只有当绿灯亮起，我们才有底气开始重构。

## 2. 消除多重嵌套：卫语句与策略模式
最常见的坏味道是深不见底的 `if-else`。

### 优化前
```java
public void processOrder(Order order) {
    if (order != null) {
        if (order.getItems() != null && !order.getItems().isEmpty()) {
            if (order.getStatus() == Status.PAID) {
                // do something
            }
        }
    }
}
```

### 优化第一步：卫语句（Guard Clauses）
尽早返回，减少缩进。
```java
public void processOrder(Order order) {
    if (order == null || order.getItems() == null || order.getItems().isEmpty()) {
        return;
    }
    if (order.getStatus() != Status.PAID) {
        return;
    }
    // do something
}
```

### 优化第二步：策略模式（针对复杂的业务分支）
如果 `if-else` 是用来区分不同类型的订单处理逻辑，策略模式是最佳解药。

定义接口 `OrderStrategy`，然后利用 Spring 的 `List<OrderStrategy>` 自动注入或者 Map 查找，彻底消除 `if-else`。

## 3. 拆分上帝类（God Class）
那个 3000 行的 `OrderService`，里面包含了下单、支付、物流、发票等所有逻辑。
利用 **单一职责原则 (SRP)** 进行拆分：
- `OrderCreationService`: 负责下单
- `PaymentService`: 负责支付交互
- `LogisticsService`: 负责物流

重构时利用 IDE（IntelliJ IDEA）的 "Extract Method" 和 "Move Method" 功能，安全高效。

## 4. 消除魔术数字
代码里满屏的 `if (status == 3)` 让人抓狂。
**必须** 定义枚举（Enum）：
```java
public enum OrderStatus {
    CREATED(0), PAID(1), SHIPPED(2), COMPLETED(3);
    // ...
}
```
这样代码就变成了 `if (status == OrderStatus.COMPLETED)`，可读性瞬间提升。

## 总结
重构不是一蹴而就的，而是“童子军规则”：**让营地比你来时更干净**。每次提交代码时，顺手做一点小的优化，积少成多，系统就会越来越健康。
