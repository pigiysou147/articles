# 重构之路：从“遗留代码”到“可维护架构”的深度思考

## 背景
在维护一些有多年历史的老项目时，我们经常发现代码里充斥着大量的 `if-else` 嵌套、千行类（God Class）以及不明所以的魔术数字。业务方催着加新功能，但每次修改都心惊胆战。

面对这种“屎山”代码，我们不能一味抱怨。作为一个技术爱好者，我们更应该思考：**为什么代码会腐化？如何用架构思维去量化和解决复杂性？**

## 1. 复杂性的量化：圈复杂度 (Cyclomatic Complexity)
在重构前，我习惯先用 Metrics 工具（如 SonarQube 或 IDEA MetricsReloaded）扫描代码。
我关注的核心指标是 **圈复杂度**。它通过计算线性独立路径的数量来衡量代码的复杂程度。

$$ V(G) = E - N + 2P $$

如果一个方法的圈复杂度超过 10，就说明它承载了过多的控制流逻辑。
**重构实战**：
对于一个圈复杂度高达 25 的订单处理方法，我没有直接上手改，而是先画出了它的 **控制流图 (CFG)**。我发现其中大量的 `if` 仅仅是为了做参数校验。
引入 **JSR-303 (Hibernate Validator)** 分组校验后，我成功将前置校验逻辑剥离，圈复杂度瞬间降到了 8。

## 2. 保护现场：AST 与 变异测试
单元测试是重构的基石，但普通的覆盖率（Line Coverage）往往会骗人。
我引入了 **Pitest (变异测试)**。它会在字节码层面修改我的代码（比如把 `i > 0` 改成 `i >= 0`），然后运行测试用例。如果测试依然通过，说明测试用例太弱，没能“杀列”变异。

```xml
<plugin>
    <groupId>org.pitest</groupId>
    <artifactId>pitest-maven</artifactId>
    <configuration>
        <targetClasses>
            <param>com.example.core.*</param>
        </targetClasses>
    </configuration>
</plugin>
```
这种“以毒攻毒”的方式，让我对测试集的信心指数级上升。

## 3. 消除多重嵌套：设计模式的深层应用

### 3.1 策略模式 + 枚举工厂
简单的策略模式大家都会，但我更喜欢结合枚举来实现**无状态策略**的快速分发。

```java
public enum OrderStrategyType {
    NORMAL {
        @Override
        public void process(Order order) { /*...*/ }
    },
    VIP {
        @Override
        public void process(Order order) { /*...*/ }
    };
    
    public abstract void process(Order order);
}
```
**技术细节**：这种写法利用了 Java 枚举的特性，编译后会生成 `OrderStrategyType$1.class` 等匿名内部类。虽然增加了少许类加载开销，但利用 JVM 的类加载锁机制，天然保证了策略实例的单例和线程安全。

## 4. 架构守护：ArchUnit
重构很容易“复胖”。为了防止后来者（包括未来的自己）破坏分层架构，我在 CI 流水线中引入了 **ArchUnit**。

```java
@AnalyzeClasses(packages = "com.example")
public class ArchitectureTest {
    @ArchTest
    static final ArchRule services_should_not_access_controllers =
            noClasses().that().resideInAPackage("..service..")
            .should().accessClassesThat().resideInAPackage("..controller..");
}
```
这就像在代码里埋下了“编译期探针”，一旦有人试图在 Service 层调用 Controller，构建直接失败。

## 总结
重构不只是清理代码，更是一场对编程语言特性、设计模式原理以及编译器行为的深度探索。
每一次 `Extract Method` 背后，都是对 **栈帧 (Stack Frame)** 深度和 **内联 (Inlining)** 优化的权衡；每一次解耦，都是对 **指令缓存 (Instruction Cache)** 友好度的考量。
保持好奇，代码深处自有黄金屋。
