# 效能提升：从 LSP 协议看 AI 编程助手的本地化实践

## 背景
在政务内网等物理隔离环境中，无法使用 GitHub Copilot。我们通过 Ollama + Continue 插件构建了本地 AI 编程助手。
但你是否好奇，IDE 插件是如何知道光标位置的上下文？AI 又是如何理解整个项目的结构的？
本文将从 **LSP (Language Server Protocol)** 和 **AST (抽象语法树)** 的角度，解析 AI 辅助编程的底层机制。

## 1. IDE 与 AI 的桥梁：LSP
在 VS Code 中，Java 支持是由 Red Hat 提供的 `vscode-java` 插件（基于 Eclipse JDT LS）实现的。
LSP 定义了一套标准 JSON-RPC 协议，用于 IDE 和语言服务器通信。

**AI 如何利用 LSP？**
当你在写代码时，Continue 插件不仅仅是将当前文件的文本发给 LLM。它会利用 LSP 获取：
1.  **Diagnostics**: 当前文件的编译错误（AI 自动修复 bug 的基础）。
2.  **Definitions**: 光标处变量的定义位置（跳转到定义）。
3.  **References**: 变量的引用列表。

通过 LSP，AI 能够获得比“纯文本”更丰富的**语义信息**。

## 2. 上下文构建策略：RAG for Code
大模型的 Context Window 有限（如 CodeGeex4 支持 128k）。如何把整个项目的代码喂给它？
这需要针对代码优化的 RAG 策略。

### 2.1 基于 AST 的切片
普通的文本切片（按行切）会破坏代码结构。
高级的 AI 助手会解析 Java 源码的 **AST (Abstract Syntax Tree)**。
它会识别出 `Class`, `Method`, `Field` 节点。在检索时，如果命中了某个方法的某一行，它会将**整个方法体**甚至**整个类**作为上下文召回，确保语义完整性。

### 2.2 依赖分析与 Graph RAG
代码文件之间不是独立的，而是引用的图结构。
Continue 插件会构建简单的依赖图。当你编辑 `Controller` 时，它会顺藤摸瓜找到对应的 `Service` 和 `Entity`，并将这些文件的摘要（Skeleton，只包含方法签名）自动加入 Prompt。
这种**基于图的检索**，比基于向量相似度的检索在代码补全场景下更加精准。

## 3. Ollama 的推理加速：Llama.cpp
在 CPU 或低端显卡上运行大模型，核心依赖 **Llama.cpp** 库。
**SIMD 指令集优化**：
Llama.cpp 针对 AVX2/AVX-512 指令集进行了极致优化，能利用 CPU 的并行计算能力进行矩阵乘法。
**KV Cache Offloading**：
如果显存不够存 KV Cache，Llama.cpp 支持将部分层（Layer）加载到 GPU，部分留在 CPU RAM，并在推理过程中动态交换数据。这使得 8G 显存的显卡也能勉强跑起来 10B 级别的模型。

## 4. Prompt Engineering for Code
代码生成的 Prompt 与对话不同，通常采用 **FIM (Fill-In-the-Middle)** 格式。
模型不仅看到光标前的代码 (Prefix)，还能看到光标后的代码 (Suffix)。
```
<PRE> public void calculate() { int a = 10; <SUF> System.out.println(result); } <MID>
```
模型需要预测 `<MID>` 部分的内容。这要求模型在预训练阶段就接触过这种格式的数据。Ollama 运行的代码模型（如 DeepSeek-Coder）原生支持 FIM，因此补全效果远好于普通的 Chat 模型。

## 总结
本地 AI 编程助手不仅仅是一个 Chatbot。它是一个集成了 **LSP 语义分析**、**AST 解析**、**图检索** 以及 **底层硬件加速** 的复杂系统。
在内网环境下，通过精细调优这些组件，我们完全可以获得媲美云端 Copilot 的体验。
