# 效能提升：从 LSP 协议看 AI 编程助手的本地化实践

## 背景
在政务内网等物理隔离环境中，无法使用 GitHub Copilot。我们通过 Ollama + Continue 插件构建了本地 AI 编程助手。
但你是否好奇，IDE 插件是如何知道光标位置的上下文？AI 又是如何理解整个项目的结构的？
本文将从 **LSP (Language Server Protocol)** 和 **AST (抽象语法树)** 的角度，解析 AI 辅助编程的底层机制。

## 1. IDE 与 AI 的桥梁：LSP

VS Code 本身并不懂 Java。它依赖 **Language Server**（对于 Java 是 Eclipse JDT LS）来提供智能感知。
LSP 定义了一套标准的 **JSON-RPC** 协议，用于 Client (VS Code) 和 Server (Java LS) 通信。

### 1.1 关键协议解析
当你在写代码时，AI 助手通过 LSP 获取了比纯文本丰富得多的信息：

*   **`textDocument/didChange`**: 实时同步代码变更。
*   **`textDocument/definition`**: 获取光标处符号的定义位置。
*   **`textDocument/references`**: 获取符号的所有引用。
*   **`textDocument/publishDiagnostics`**: 获取编译错误和警告。

**AI 如何利用 LSP？**
当你要修复一个 Bug 时，Continue 插件不仅仅是将当前文件的文本发给 LLM。它会捕获 `publishDiagnostics` 中的错误信息（例如 "NullPointerException at line 10"），并将其作为 Prompt 的一部分：“请修复第 10 行的空指针异常”。
这使得本地小参数模型（如 DeepSeek-Coder-7B）也能表现出惊人的修复能力，因为它拥有了“编译器视角”。

## 2. 上下文构建策略：RAG for Code

大模型的 Context Window 有限（如 CodeGeex4 支持 128k）。如何把整个项目的代码喂给它？
这需要针对代码优化的 RAG 策略。

### 2.1 基于 AST 的切片 (Tree-sitter)
普通的文本切片（按行切）会破坏代码结构。例如，把一个函数切成两半，模型就懵了。
高级的 AI 助手（如 Continue）集成了 **Tree-sitter** 解析器。它能极快地解析源码构建 **AST (Abstract Syntax Tree)**。

**AST 切片策略**：
它会识别出 `class_declaration`, `method_declaration` 等节点。
在检索时，如果命中了某个方法的某一行，它会将**整个方法体**甚至**整个类**作为上下文召回，确保语义完整性。

### 2.2 依赖分析与 Graph RAG
代码文件之间不是独立的，而是引用的图结构。
Continue 插件会构建简单的依赖图。
当你编辑 `OrderController.java` 时，它会解析 `import` 语句，顺藤摸瓜找到 `OrderService.java` 和 `Order.java`。
并将这些关联文件的**摘要 (Skeleton)**（只包含方法签名，去除了实现细节）自动加入 Prompt。

这种**基于图的检索**，比基于向量相似度的检索在代码补全场景下更加精准。它解决了“模型不知道我定义了什么新类”的问题。

## 3. Ollama 的推理加速：Llama.cpp

在 CPU 或低端显卡上运行大模型，核心依赖 **Llama.cpp** 库。它使得在普通 PC 上跑 LLM 成为可能。

### 3.1 SIMD 指令集优化
矩阵乘法是 LLM 推理最耗时的操作。
Llama.cpp 针对 CPU 的 **AVX2 / AVX-512** 指令集进行了极致优化。
它利用 SIMD (Single Instruction, Multiple Data) 技术，一次指令处理多个数据，大幅提升了 CPU 推理速度。

### 3.2 KV Cache Offloading
如果显存不够存 KV Cache，Llama.cpp 支持 **Layer Offloading**。
它可以将模型的 32 层中，前 20 层放在 GPU 上跑，后 12 层放在 CPU 上跑。
虽然 CPU 慢，但 PCIe 带宽通常足够支持这种流水线并行。这使得 8G 显存的显卡也能勉强跑起来 10B 级别的模型。

## 4. Prompt Engineering for Code

代码生成的 Prompt 与对话不同，通常采用 **FIM (Fill-In-the-Middle)** 格式。
模型不仅看到光标前的代码 (Prefix)，还能看到光标后的代码 (Suffix)。

**Prompt 格式示例**：
```
<PRE> 
public void calculate() { 
    int a = 10; 
<SUF> 
    System.out.println(result); 
} 
<MID>
```
模型需要预测 `<MID>` 部分的内容。
这要求模型在预训练阶段就接触过这种格式的数据。Ollama 运行的代码模型（如 DeepSeek-Coder）原生支持 FIM，因此中间补全的效果远好于普通的 Chat 模型。

## 总结
本地 AI 编程助手不仅仅是一个 Chatbot。
它是一个集成了 **LSP 语义分析**、**Tree-sitter AST 解析**、**图检索** 以及 **底层硬件加速 (SIMD/CUDA)** 的复杂系统。
在内网环境下，通过精细调优这些组件，我们完全可以获得媲美云端 Copilot 的体验，同时守住数据安全的底线。
