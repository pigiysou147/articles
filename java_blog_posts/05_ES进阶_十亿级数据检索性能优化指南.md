# ES 进阶：十亿级数据检索性能优化指南

## 背景
随着业务日志数据量激增，Elasticsearch (ES) 集群的响应可能会越来越慢。查询经常超时，Kibana 面板转圈圈。面对 10 亿级的数据量，默认配置往往难以支撑。本文总结了常见的性能调优策略。

## 1. 写入性能优化
在数据导入或大规模同步阶段，写入速度是瓶颈。

### 1.1 客户端优化
- **Bulk 批量操作**：绝对不要一条一条写。使用 Bulk API，每批次建议 5MB-15MB（约几千条）。
- **多线程写入**：Java 客户端使用多线程并发 Bulk。

### 1.2 服务端配置
- **Refresh Interval**: 默认 1s。这意味着每秒都会生成新的 Segment，导致大量 I/O。
  *   *优化*：导入期间设为 `-1` 或 `30s`。
  *   `PUT /my_index/_settings { "index" : { "refresh_interval" : "30s" } }`
- **Translog**: 默认每请求都落盘（request）。
  *   *优化*：改为异步（async），每 5s 落盘一次。牺牲一点数据安全性换取性能。

## 2. 查询性能优化
这是用户感知最明显的地方。

### 2.1 避免 Deep Paging (深度分页)
不要做 `from=10000, size=10` 这种查询！
ES 需要从每个分片取前 10010 条数据，汇总后再排序。越往后越慢，甚至 OOM。
*   **解法**：使用 `search_after` 游标查询。

### 2.2 Filter 缓存
- `Query` 上下文会计算相关性算分 (_score)。
- `Filter` 上下文**不计算算分**，且结果会被**缓存**。
*   *优化*：对于不需要模糊匹配的字段（如 status, category_id），统统放入 `filter` 中。

```json
GET /_search
{
  "query": {
    "bool": {
      "must": [ { "match": { "title": "Java" } } ],
      "filter": [ { "term":  { "status": "published" } } ]
    }
  }
}
```

### 2.3 路由 (Routing)
默认情况下，ES 会查询所有分片。
如果在写入时指定了路由（如 `user_id`），查询时也带上：
`GET /_search?routing=user_123`
这样 ES 只需查询 1 个分片，性能提升 N 倍（N=分片数）。

## 3. 硬件与架构
- **SSD 是必须的**：不要用机械硬盘。
- **冷热分离**：
  *   热节点：高性能 CPU/IO，存最近 7 天数据。
  *   冷节点：大容量磁盘，存历史数据。
  *   利用 Index Lifecycle Management (ILM) 自动迁移。

## 总结
ES 优化没有银弹，核心是**减少 I/O** 和 **减少计算**。
1. 写入用 Bulk + 调大 refresh_interval。
2. 查询多用 Filter，拒绝深度分页。
3. 合理规划分片和路由。
